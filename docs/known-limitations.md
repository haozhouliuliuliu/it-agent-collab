# 已知限制

## 1. 范围

- 全部企业数据、制度、工单均为虚构；只做分析与建议，不执行任何业务写入；
- 不连接真实 IT 系统、资产系统或采购流程；没有写工具、SQL、命令、文件访问入口。

## 2. 模型与结构化输出

1. **结构化输出依赖模型**：Planner/Business/Policy/Auditor 都要求 JSON；模型可能输出非法 JSON、超长或被截断。
   - 已做：一次修复调用；审核失败时用更短提示重试；仍失败则返回 `needs_evidence` 并记录 `audit_unavailable`；
   - 未做：函数调用强制 schema（不同供应商支持不一致）。
2. **供应商差异**：Kimi 只接受 `temperature=1`，且账户限流约 3 RPM；Qwen 对 `max_tokens` 的执行不一致；这些在配置和限流器里做了适配，但仍可能波动。
3. **审核摘录有上限**：审核 Agent 看到的证据 `excerpt` 截断到 4000 字符；极长的工单列表可能被截断，审核会因此报"来源未出现"。
4. **没有多模型投票**：一个角色固定一个模型；没有同一结论的多模型交叉验证。

## 3. 调度与协作

1. **Planner 决定是否派 Policy**：程序只强制 Business；纯数据问题可能不派 Policy，这是设计意图，但也意味着 Planner 漏判时不会有制度视角。
2. **并行只发生在 Business/Policy 之间**：审核必须等两者结束；没有流水线式重叠。
3. **返工只支持一轮**：`needs_evidence` 时有 followup 才返工；返工目标按关键词选择（制度 vs 业务），可能选错。
4. **评估中关闭了返工**：为把真实调用控制在 50 次内，最终评估设置 `COLLAB_REVISION_LIMIT=0`；返工能力由自动化测试覆盖，而非最终评估。

## 4. 状态与部署

1. **单进程 SQLite**：WAL 支持轻量并发，但不适合多副本/高并发；没有任务队列。
2. **无 HTTP API/认证/TLS**：只有 CLI；任何能执行命令的人都能运行任务。部署到共享环境需要外层包装。
3. **无流式输出**：任务结束后一次性打印；长任务需要等待。
4. **无成本看板**：记录 token 与调用次数，但不计算金额。

## 5. 评估局限

1. **单轮最终评估**：模型有随机性；换时间/模型需要重跑。
2. **首轮失败已保留**：第一轮 6/8（M3 审核 JSON 截断、M6 预算耗尽），修复后重跑；报告同时记录两轮，不删除失败。
3. **真实调用总量**：首轮 50 次 + 最终轮约 40 次，超过"单轮 50 次"的建议上限；最终轮本身控制在 50 次内，首轮作为失败迭代保留。
4. **结构化断言**：判定基于状态、Agent 集合、审核 verdict、关键文本与调用模型，不评价文字质量。
5. **2 个简单用例不经过审核**：用于验证路由，不作为多 Agent 能力证据。

## 6. 刻意不做

- 多租户、SSO、权限平台；
- 集群部署、监控告警；
- 真实企业系统接入与业务写入；
- 多 Agent 自由对话/辩论（当前是结构化交接 + 独立审核）。
